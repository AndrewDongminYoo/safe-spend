# Ledger Consistency Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:test-driven-development` for every production change and `superpowers:executing-plans` for inline execution.

**Goal:** Correct the five reviewed transition and persistence defects that can inflate or understate safe-to-spend money.

**Architecture:** Add an explicit in-memory persistence mode at the application-store boundary, migrate persisted financial state to a revision-aware version 2 schema, and centralize recurring occurrence generation while keeping completed history immutable.
Domain transitions remain pure and platform-free.

**Tech Stack:** React 18, strict TypeScript, Vitest 5, React Testing Library, Apps in Toss Storage adapter

**Spec:** `docs/specs/2026-09-23-ledger-consistency.md`

## Global Constraints

- Preserve the existing `package.json` working-tree change and do not add dependencies.
- Keep money as safe non-negative integer won amounts and dates as validated `YYYY-MM-DD` values.
- Persist only version 2 snapshots after load or mutation.
- Preserve paid and skipped occurrence history.
- Never call repository persistence in session mode.
- Do not commit, push, or publish without a separate explicit request.

## Review Focus

- A settings submission that changes only the reserve or income date must not invalidate current-revision refunds.
- A late renewal must include the confirmation-day bill without duplicating an occurrence already generated by the old cycle.
- Reconciliation must not rewrite paid or skipped historical names, amounts, dates, or revisions.
- Migrated version 1 deductions must not become refundable against an untraceable absolute balance.
- Session reset and retry paths must not touch a recovered repository.
